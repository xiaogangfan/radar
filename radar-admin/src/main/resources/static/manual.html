打分字段（规则表单里的 6 项）

术语解释
初始得分规则命中即给的固定底分，任何操作符都影响不到它
命中基数与指标值做四则运算的左操作数
操作符无 / 加 / 减 / 乘 / 除，决定基数和指标值怎么算
指标字段（特征字段）参与运算的变量，可选字段或抽象值
比率给指标值做缩放，单位是百分数（100 = 1.0×，50 = 0.5×）
最大值本条规则的分数上限，0 = 不封顶
警戒值 / 拒绝值策略上的两条线：总分 ≥ 警戒值 → review，≥ 拒绝值 → reject

步涉及术语本例发生了什么
1字段业务方传入 userIP=1.2.3.4、deviceId=dev-3、loginTime=…
2预处理手机号 13800000001 → 号段 1380000

两个硬规矩：
1. 抽象用到的字段必须勾"是否索引"。勾了索引，Mongo 端才会建 (字段, loginTime) 复合索引；不勾，滑窗查询会退化成全表扫。
2. 字段名必须和业务方 JSON 里的 key 一模一样（大小写敏感）。引擎按名取值，取不到就当 null，不报错——这是"配完不生效"的第一大原因。

7.3 打分公式

引擎按下面这条式子算每条规则的得分（源码 AntiFraudEngineImpl）：

规则得分 = 初始得分 + (命中基数 操作符 (指标字段值 × 比率%))
           └ 最大值 > 0 时，结果封顶到最大值
策略总分 = Σ 各条命中规则的得分

总分 ≥ 拒绝值(80)              → reject
警戒值(40) ≤ 总分 < 80         → review
总分 < 40                      → pass

四种操作符（V = 指标字段值，R = 比率）：

操作符规则得分适用
无初始得分命中即固定分，指标字段被禁用
加初始得分 + 命中基数 + V×R%指标越大分越高
减初始得分 + 命中基数 − V×R%指标越大分越低
乘初始得分 + 命中基数 × V×R%基数当系数，最常用
除初始得分 + 命中基数 ÷ (V×R%)保留 2 位小数

三个算例

场景配置计算结果
本例（二值）初始 100 / 操作符 无100≥80 → reject；不命中 → 0 → pass
236 线上规则初始 20 / 基数 1 / 乘 / 比率 100 / 指标「1天内IP关联用户数」=1320 + 1×1333 → review
梯度打分A 规则 ≥3 台加 60，B 规则 ≥10 台再加 5060 或 60+50命中 A → review，A+B → reject
四个坑：
1）最大值 0 是不封顶，不是 0 分；要限制上限就填正数。
2）乘 + 命中基数 0 是死配置：0 × 任何值 = 0，指标字段白配。
3）除没有除零保护：V×R% 为 0 时抛异常，整个请求 500。
4）被抽象过滤掉的事件，指标值是 -1：会原样参与运算（乘 → 扣分）。

08激活并验证

8.1 开开关

模型右上角的总开关 + 策略行的开关都要开（见 §7.1 截图）。配置经 Redis 发布订阅热推给引擎，不用重启。

8.2 单发验证

下面这条 curl 就是模型 236（电商-营销防刷）的真实调用（GUID 取自「模型列表接口」），可直接复制执行：

TS=$(date +%s)000   # 毫秒时间戳；macOS 的 BSD date 不支持 %3N，直接补三个 0
curl -s -X POST http://127.0.0.1:6582/services/v1/upload \
  -H 'Content-Type: application/json' \
  -d "{
    \"guid\": \"E48E20E0-4B47-4152-B21D-486F1C51500B\",
    \"reqId\": \"verify-1\",
    \"jsonInfo\": {
      \"loginTime\": ${TS},
      \"userId\": \"u1\", \"eventId\": \"evt-1\",
      \"userIP\": \"9.9.9.9\", \"deviceId\": \"d1\",
      \"mobile\": \"13800000001\",
      \"passwd\": \"x\", \"os\": \"app\", \"channel\": \"app\"
    }
  }"
loginTime 怎么填：必须是 13 位毫秒时间戳（纯数字、不加引号）——10 位秒会被当成 1970 年，抽象窗口全部落空、分数恒为 0。
滑窗是以事件自己的 loginTime 为基准往前取（实测：把 loginTime 写成 1 小时前，同 IP 换 3 设备照样触发 reject/100）。所以复现场景时整批请求用同一个值即可，不必每次重算。

实测返回（首次必然 pass，因为 Mongo 里还没有这个 IP 的历史；abstractions 是 14 个滑窗指标，此处节选）：

{"success":true,"msg":"","code":"100","data":{},
 "abstractions":{"log_ip_10_min_qty":1,"log_did_ip_10_min_qty":1, ...},
 "activations":{"login_exception":{"risk":"pass","score":0}},
 "hitsDetail":{"login_exception":[]}}
activations 的 key 是策略名，risk 是决策、score 是总分；hitsDetail 列出命中的规则。换模型时只要替换 guid，其余不变。
返回字段速查
{
  "success": true,        // 整条链路是否跑通，false 时看 msg
  "msg": "",              // 失败原因（模型不存在 / 参数校验不通过 / 时间不正确）
  "code": "100",          // 业务码，100 = 成功
  "data": {},             // 校验失败时才有内容（哪个字段不合法）
  "abstractions": {       // ★ 抽象层：14 个滑窗指标，值 = 窗口内满足条件的量
    "log_ip_1_day_qty": 4,       // 同 userIP 近 1 天登录次数 → 4
    "log_uid_1_day_qty": 3,      // 同 userId 近 1 天登录次数 → 3
    "log_did_ip_1_day_qty": 3,   // 同 userIP 近 1 天几个不同 deviceId → 3
    "log_ip_1_hour_qty": 0,      // 同 userIP 近 1 小时登录次数 → 0
    "log_ip_10_min_qty": 0,      // 同 userIP 近 10 分钟登录次数 → 0
    "log_did_ip_10_min_qty": 0   // 同 userIP 近 10 分钟几个不同 deviceId → 0（本例规则的输入）
  },
  "adaptations": {},      // 预处理（黑/白名单等）产出，默认空
  "activations": {        // ★ 策略层：每个策略一个决策
    "login_exception": { "risk": "pass", "score": 0 }   // risk=pass/review/reject，score=命中规则总分
  },
  "hitsDetail": {         // ★ 命中明细：只列触发的规则（id / 加分 / 描述）
    "login_exception": []
  },
  "respTimes": { "adaptations": 12, "activations": 1, "abstractions": 107 }  // 各阶段耗时(ms)
}

指标命名规律（看名字就知道在算什么）：log_ + ip/uid/did = 按 IP/用户/设备统计次数；多一个 _ip（如 log_did_ip）= 按 IP 分组数去重值→"几个设备/几个账号"；结尾 _10_min / _1_hour / _1_day = 统计窗口。

⚠️ 看到"1 天有值、1 小时和 10 分钟全是 0"别以为配错了——通常说明本次事件没入库。entity_236 以 eventId 去重：同一 eventId 重复提交只留第一条，后续直接丢弃。事件没写进去，滑窗自然查不到它自己。
实测：用 §8.2 的参数再跑一次（eventId 仍是 evt-1），返回与第一次完全一致，1_hour/10_min 恒为 0、1_day 仍是 4（历史数据）。验证时每次都要换 eventId，否则会误判成"规则没生效"。

8.3 复现攻击场景

同一 IP 换 3 个设备连打 3 次（注意每次换 deviceId 和 eventId；用全新 IP 7.7.7.7 避免和历史数据混淆）：

GUID="E48E20E0-4B47-4152-B21D-486F1C51500B"; TS=$(date +%s)000
for i in 1 2 3; do
curl -s -X POST http://127.0.0.1:6582/services/v1/upload -H 'Content-Type: application/json' \
  -d "{\"guid\": \"$GUID\",\"reqId\": \"demo-$i\",\"jsonInfo\": {\"loginTime\": $TS,\"userId\": \"demo-$i\",
  \"eventId\": \"evt-demo-$i\",\"userIP\": \"7.7.7.7\", \"deviceId\": \"dev-$i\",\"mobile\": \"1380000000$i\",
  \"passwd\": \"x\", \"os\": \"app\", \"channel\": \"app\"}}" | python3 -m json.tool | grep -A3 activations
done
第几次deviceId引擎返回原因
1dev-1pass / score=0窗口内该 IP 只有 1 台设备
2dev-2pass / score=02 台 < 3，未到阈值
3dev-3reject / score=100distinct(deviceId)=3，规则命中加 100 ≥ 拒绝值 80

第 3 次的完整返回片段：

"activations": {"login_exception": {"risk": "reject", "score": 100}},
"hitsDetail": {"login_exception": [{"key": "442", "value": 100.0, "desc": "10分钟内IP关联设备数大于等于3"}]}

再换一个新 IP（如 6.6.6.6）打一次 → 又是 pass / score=0。这就是"同 IP 换设备"规则生效的完整证据链。

8.4 这次请求在引擎里发生了什么

业务方POST /upload，jsonInfo 带 9 个字段

MongoDB14 个抽象滑窗查询（含本例的 distinct deviceId）

09能力地图：六大业务能配哪些场景

配不出来的场景通常不是"配置没写对"，而是这套引擎只有下面 7 类原子能力，超出范围就得换思路：

能力具体支持硬限制
字段字符串 / 整数 / 长整型 / 浮点名字必须与业务 JSON 的 key 一致，取不到即 null
预处理插件IP 转地址、手机号归属地、GPS 转地址、字符串截短、字段合并、时间格式化、敏感时间段、HTTP 调用一个衍生字段只挂一个插件；HTTP 插件是同步阻塞调用
黑白名单精确字符串匹配，系统名单跨模型共享无正则/前缀/区间；多字段按逗号拼成一串
抽象指标count / distinct count / sum / avg / max / min，窗口 秒~年圈定范围只有一个等值搜索字段
条件前缀、包含、等于、大小比较、在名单中、为空 + All/Any/NotAll/None 组合只能组合字段与抽象值，不认识"事件序列"
打分初始得分 + 基数四则运算（加/减/乘/除），可设上限单条规则只引用一个指标字段
策略多策略并行，警戒/拒绝双阈值输出只有 pass / review / reject + 分数
引擎只负责判定和打分：封号、拦截下单、限制发券这些动作要业务侧按返回的 risk 自己执行。

9.7 配不出来的需求，怎么变通

需求为什么不行变通
多键联合滑窗（user + device + ip 同时限定）搜索字段只能一个等值条件每个键各配一个抽象，规则里用 All 组合
团伙 / 图谱关联没有图存储，只能数"不同值有几个"用 distinct count 近似（同 IP 关联账号数、同设备关联用户数）
行为序列（N 分钟内先注册后下单）抽象是聚合值，不保存事件顺序两个窗口差值近似，或业务侧打标成字段后判断
名单正则 / 号段前缀匹配名单是精确字符串比对先用「字符串截短」预处理，再拿截短结果入名单
黑产库自动同步只能页面导入或接口导入调 POST /services/v1/datalist/batchImportData（≤1000 条/次）定时推
实时外部特征（征信、设备指纹）只有同步 HTTP 插件接受同步延迟，或用离线补数 + 缓存表

9.8 从 0 到 1 的落地顺序

① 先上名单：设备、手机号、IP 是最便宜的一层，0 计算成本，命中即 reject。
② 再选 3~5 个指标：覆盖注册、登录、下单、支付、提现这 5 个关键动作，每个都用"单键 × 单窗口"，别贪多。
③ 每指标配两档：先只开 review 观察，确认误杀率后放开 reject。
④ 跑 1~2 周再看组合：稳定后再做多键组合与更细的分档。
