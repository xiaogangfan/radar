# 详细设计：模型业务线与场景维度

关联 PRD：docs/PRD-模型业务线与场景.md（V1.5，REQ-2026-09-001）
涉及模块：radar-commons / radar-dao / radar-dal / radar-service / radar-service-impl / radar-admin / 前端工程（源码不在本仓库，见第 6 节）
不涉及：radar-engine（评估链路不读这两个字段，无需改动）

---

## 1. 总体思路

业务线不建表，用代码枚举 `BusinessLineType` 提供（编码 + 中文名），后续公司基础服务统一供给业务线数据时替换数据源（见 2.2 的扩展点）。场景单独建表 `engine_scene`，用 BUSINESS_LINE 列存业务线编码。模型表加 BUSINESS_LINE（编码）和 SCENE_ID 两列。管理后台按「业务线 → 场景 → 模型」三级组织，模型列表页左侧一棵树，点树节点过滤右侧表格。

命名上有一个容易踩的坑要先说明：`engine_model` 已有 `CODE` 列，语义是 merchantCode（商户标识，登录用户上下文带进来的），和业务线/场景的 CODE（编码）不是一回事。编码只在枚举和 engine_scene 里使用，不和模型 CODE 发生任何关联，代码里也不要把两者混进同一个 VO 字段。

## 2. 业务线枚举设计

### 2.1 枚举定义（radar-commons）

放 `com.pgmmers.radar.enums.BusinessLineType`，风格对照现有 `StatusType`：

```java
public enum BusinessLineType {
    ECOMMERCE("ecommerce", "电商"),
    LOCAL_LIFE("local-life", "本地生活"),
    ERRAND("errand", "跑腿"),
    SOCIAL("social", "社交"),
    MOBILITY("mobility", "出行"),
    HEALTHCARE("healthcare", "大健康"),
    METAVERSE("metaverse", "元宇宙"),
    UNCLASSIFIED("unclassified", "未分类");

    private final String code;
    private final String name;
    // 构造器 + getter + 静态方法
    public static BusinessLineType of(String code) { ... }   // code -> 枚举，找不到返回 null
}
```

「未分类」作为枚举固定值参与树和下拉展示，排序恒在最后，不可挂新场景（新增场景的业务线选项里排除 unclassified——它是存量模型的兜底归属，不是可运营的业务线）。

### 2.2 数据源扩展点

后续基础服务供给业务线数据时的替换方式（本期不实现，只保证不返工）：

- 枚举是唯一数据源，前后端都通过接口拿业务线列表（前端不硬编码业务线），替换时只改后端 `GET /dimension/businessLine/list` 和 `tree()` 的实现，接口契约不变。
- engine_scene.BUSINESS_LINE、engine_model.BUSINESS_LINE 存的是编码而非自增 ID，基础服务上线后编码若一致则历史数据无缝；若编码有出入，一次性 UPDATE 迁移（两张表都是小表）。

## 3. 数据库设计

### 3.1 建表（仅场景）

```sql
CREATE TABLE `engine_scene` (
  `ID` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '主键',
  `BUSINESS_LINE` varchar(64) NOT NULL COMMENT '所属业务线编码（BusinessLineType.code）',
  `NAME` varchar(64) NOT NULL COMMENT '场景名称',
  `CODE` varchar(64) NOT NULL COMMENT '场景编码，全局唯一，小写中划线',
  `STATUS` int(11) NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  `SORT` int(11) NOT NULL DEFAULT 0 COMMENT '排序号，小的在前',
  `CREATE_TIME` datetime DEFAULT NULL,
  `UPDATE_TIME` datetime DEFAULT NULL,
  PRIMARY KEY (`ID`),
  UNIQUE KEY `uk_code` (`CODE`),
  KEY `idx_business_line` (`BUSINESS_LINE`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='风险场景字典';
```

SCENE_ID 上不加索引：模型表数据量小（配置表，百级），过滤走全表可接受；真有需要后续再加。

### 3.2 engine_model 加列

```sql
ALTER TABLE `engine_model`
  ADD COLUMN `BUSINESS_LINE` varchar(64) DEFAULT NULL COMMENT '业务线编码' AFTER `CODE`,
  ADD COLUMN `SCENE_ID` bigint(20) DEFAULT NULL COMMENT '场景ID' AFTER `BUSINESS_LINE`;
```

存量 5 个模板模型两列均为 NULL，前端归入「未分类」节点展示，不做数据回填。

### 3.3 初始数据

场景：电商下 4 条（marketing-anti-brush 营销防刷 / account-safety 账户安全 / payment-anti-fraud 支付反欺诈 / merchant-fraud 商家刷单），本地生活/跑腿/社交/出行/大健康/元宇宙各 1 条「账户安全」（CODE 加业务线前缀避免全局唯一冲突，如 errand-account-safety），unclassified 下 1 条 pending 待归类。

以上 DDL 和初始数据同步进 sql/radar-init.sql（users 表补列那次就是这么做的，保持同一做法）。

### 4.2 radar-dal

新增 `com.pgmmers.radar.dal.dimension` 包：

```
SceneDal                  / impl/SceneDalImpl
```

接口方法（实现全部用 tk.mybatis Example，无 XML）：

```java
public interface SceneDal {
    List<ScenePO> listByBusinessLine(String businessLine, Integer status);
    List<ScenePO> listAll();                            // 树/计数用
    ScenePO getById(Long id);
    int save(ScenePO po);                               // id null 走 insertSelective，否则 updateByPrimaryKeySelective
    int delete(Long id);
    ScenePO getByCode(String code);                     // CODE 全局唯一校验用
    long countModel(Long sceneId);                      // 删除校验：该场景下模型数（查 engine_model）
    Map<Long, Long> countModelGroupByScene();           // 树节点计数：sceneId -> modelCount
    long countUnclassified();                           // engine_model 中 SCENE_ID IS NULL 的数量
    List<ScenePO> listByIds(List<Long> ids);            // 列表补名用
}
```

countModelGroupByScene 用 Example 查 engine_model 的 SCENE_ID 列再内存分组（配置表量级小，不引入 group by SQL）。

修改 `ModelDalImpl`：

- `query(ModelQuery)`：criteria 追加三个条件——`query.getBusinessLine() != null` 时 `andEqualTo("businessLine", ...)`，`query.getSceneId() != null` 时 `andEqualTo("sceneId", ...)`，`query.isOnlyUnclassified()` 为 true 时 `andIsNull("sceneId")`。
- `listModel` 系列不动。

### 4.3 radar-service / radar-service-impl

`radar-service` 新增 `com.pgmmers.radar.service.dimension.DimensionService`，VO 放 `com.pgmmers.radar.vo.dimension`：

```java
public interface DimensionService {
    CommonResult tree();                                // 左树数据
    CommonResult listBusinessLine();                    // 业务线列表（枚举数据）
    CommonResult listScene(String businessLine);        // 某业务线下场景
    CommonResult saveScene(SceneVO vo);
    CommonResult deleteScene(Long[] ids);
}
```

`DimensionServiceImpl` 关键逻辑：

**saveScene 校验**（顺序固定，先格式后唯一）：

```
NAME 空                        → "名称不能为空"
CODE 空/格式错                 → "CODE不能为空" / "CODE仅允许小写字母、数字、中划线"
BUSINESS_LINE 空               → "请选择业务线"
BUSINESS_LINE 非 unclassified 且枚举中不存在 → "业务线不存在"
CODE 已存在                    → "CODE已存在"（getByCode，编辑时排除自身 id）
```

**删除校验**：

```
deleteScene: countModel(id) > 0 → "该场景下有N个模型，不可删除"
批量删除逐条校验，任何一条不通过则整体不删，返回第一条的错误信息（与现有 delete 风格一致）。
```

**listBusinessLine**：遍历 BusinessLineType（unclassified 置底），附加各业务线场景数与模型数（模型数来自 countModelGroupByScene 按 scene.businessLine 分组求和）。响应项：`{ code, name, sceneCount, modelCount }`。

**tree() 组装**（每次请求实时算，场景不进缓存，业务线读枚举）：

```
1. BusinessLineType.values() 为骨架（unclassified 置底），每条业务线挂 listByBusinessLine(code, null) 的场景列表（按 SORT,ID 排序）
2. countModelGroupByScene() 一次查出 sceneId->modelCount，填到场景节点；业务线节点 modelCount = 下属场景求和
3. countUnclassified() 填「未分类」节点计数
4. 无场景且无模型的业务线节点照常展示（来自枚举，保持结构稳定）
```

响应结构（tree 节点 VO）：

```json
{
  "success": true,
  "data": {
    "tree": [
      { "code": "ecommerce", "name": "电商", "modelCount": 3,
        "children": [
          { "id": 11, "name": "营销防刷", "code": "marketing-anti-brush", "status": 1,
            "sort": 0, "modelCount": 2 }
        ] },
      { "code": "unclassified", "name": "未分类", "modelCount": 5, "children": [ ... ] }
    ]
  }
}
```

### 4.4 模型保存改造（ModelServiceImpl.save）

在现有「模型名称重复」校验之后、`modelDal.save` 之前插入：

```
if (model.getSceneId() == null || StringUtils.isEmpty(model.getBusinessLine())) {
    return fail("请选择业务线和场景");
}
ScenePO scene = sceneDal.getById(model.getSceneId());
if (scene == null) return fail("场景不存在");
if (!scene.getBusinessLine().equals(model.getBusinessLine())) {
    return fail("场景不属于该业务线");
}
if (model.getId() == null) {   // 仅新建校验启用态；编辑允许保留已停用的归属
    if (scene.getStatus() != 1) return fail("场景已停用");
}
```

业务线编码合法性由场景归属校验间接保证（场景的 BUSINESS_LINE 一定经过 saveScene 校验来自枚举），模型侧不再单独校验枚举存在性。

`ModelServiceImpl` 注入 SceneDal 即可。保存成功后的 `cacheService.publishModel(model)` 原样保留——ModelVO 多了两个字段对 engine 无副作用（engine 不读）。

### 4.5 模型 VO 与列表补名

`radar-service` 的 `vo/model/ModelVO.java` 加字段：`businessLine`（String 编码）、`sceneId`、`businessLineName`、`sceneName`（后两个仅展示用，MapStruct 按同名自动映射前两个）。

补名位置放在 `ModelServiceImpl.query()` 返回前：把当页模型的 sceneId 去重，一次 `sceneDal.listByIds` 批量查，内存填 sceneName；businessLineName 用 `BusinessLineType.of(code).getName()` 填，不查库。**不在 Dal 层做 join**，和现有代码风格一致。

`ModelQuery` 加 `businessLine`（String）、`sceneId`（Long）、`onlyUnclassified`（Boolean）字段。

### 4.6 radar-admin

新增 `DimensionApiController`，路由和注解风格照抄 ModelApiController：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /services/v1/dimension/tree | 左树 |
| GET | /services/v1/dimension/businessLine/list | 业务线列表（枚举数据 + 计数） |
| GET | /services/v1/dimension/scene/list/{businessLine} | 某业务线下场景 |
| PUT | /services/v1/dimension/scene | 保存场景 |
| DELETE | /services/v1/dimension/scene | 删除，body 为 Long[] |

业务线没有保存/删除接口——枚举数据，维护走研发发版。Controller 只做参数透传，校验逻辑全部在 Service。`/services/v1/**` 已被 AuthInterceptor 覆盖，登录态天然生效，不需要额外配置。

模型侧已有接口的变更点：

- `GET /services/v1/model/list` 与 `POST /services/v1/model`（query）：响应 VO 带 businessLine/sceneId/businessLineName/sceneName，query 支持三个新过滤字段。
- `PUT /services/v1/model`：请求体 ModelVO 接受 businessLine/sceneId，走 4.4 的校验。

## 5. 缓存与一致性

- 场景字典**不进**任何本地缓存，每次查库；业务线读枚举，零开销。理由：只有 admin 后台读它，QPS 极低；避免再引入一套字典缓存失效逻辑。
- 模型缓存链路（BaseLocalCacheService + Redis subscribe/publishModel）不感知维度变化。场景的增删改不影响模型缓存，也不需要 publish——engine 不消费这两个字段。改模型归属时模型本身变了，走原有 publishModel，engine 侧缓存刷新照旧。
- engine_scene 写入量极小，唯一性靠 DB 唯一索引兜底，Service 层校验先行（DB 抛 DuplicateKeyException 时统一转成"CODE已存在"返回，需要在 Controller 加一层异常捕获或全局 handler）。

## 6. 前端设计

前端源码不在本仓库（radar-admin/src/main/resources/static 下是构建产物），以下为前端工程的改动说明，按 PRD 3.1–3.4 的路由执行。

**/modelList 改造**

- 布局改为左树右表，左树宽约 240px，数据源 `GET dimension/tree`。
- 树节点：业务线节点带 children（场景）+ modelCount 徽标；「未分类」为固定根节点，点击过滤 `onlyUnclassified=true`。
- 点击业务线节点 → query 传 businessLine（编码）；点击场景节点 → 传 sceneId。切节点重置 pageNo=1。
- 表格在「状态」列前加「业务线 / 场景」两列，值取 businessLineName/sceneName，NULL 显示 —。
- 「新建模型」按钮点击先弹级联选择（el-cascader，数据源同一棵树，只出 status=1 的场景、业务线不含未分类），选定后携带 businessLine/sceneId 跳 /model/0（新建）。

**/model/:id 表单**

- 顶部加「归属」字段：el-cascader（业务线→场景），value 为 [businessLineCode, sceneId]，必填规则同现有 modelName。编辑态回显时按模型 businessLine/sceneId 定位选中项。
- 从 /modelList 树节点进入时预填且可修改。

**/dimension 新页（场景管理）**

- 路由 /dimension，菜单挂「系统管理」下（具体菜单树由前端工程定）。
- 左侧业务线分组导航（`GET businessLine/list`，固定不可增删改，「未分类」置底）；右侧当前业务线的场景 CRUD。
- 表单字段：名称（必填）、CODE（必填，前端先做 `^[a-z0-9-]+$` 正则）、排序号、状态开关。
- 删除二次确认弹窗；后端返回"不可删除"类错误时直接 Toast 后端 msg。
- 业务线不出现任何新增/编辑/删除入口（验收第 8 条）。

## 7. 上线与回滚

上线顺序：

1. 执行 DDL（建 engine_scene + engine_model 加两列）——加列对旧代码无影响（selective 更新、resultMap 不认识的列不映射）。
2. 执行初始场景数据 INSERT。
3. 后端发布（admin 与 engine 可以同版本发布；engine 实际无代码改动，跟着大版本走即可）。
4. 前端发布。

回滚：代码回旧版本即可，两列和场景表留着无副作用；如需彻底回滚，DROP TABLE engine_scene + ALTER DROP COLUMN（存量模型两列本来就是 NULL，无数据损失）。
